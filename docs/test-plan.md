# Security and functional test plan

**Status update 2026-10-18.** This plan was written before deployment. Tests have since been run; actual outcomes are only in [results](results.md). Test IDs marked "added" below were created during execution. Do not read this page as a results page. Every test needs an approved deployment, exact local-only configuration snapshot, UTC start/end times and evidence. Do not enable public access, trusted bypass or broader allowlists to make a test pass **unless the owner explicitly approves a labelled control experiment** (CMK-CONFIG-02).

## Evidence protocol

For each test preserve: approved configuration manifest/version, relevant ARM properties and provisioning/PE approval states, DNS answers, actual socket peer IP/TLS hostname checks, authentication identity alias, request/correlation IDs, bounded retry window and original errors. Raw JSON, diagnostic logs, actual IPs/IDs and authentication context stay in ignored local evidence. Never log Authorization headers/tokens, key material or secrets. Public results contain sanitized summaries and evidence **aliases**, not raw logs.

Capture configuration immediately before and after tests so a successful operation is not attributed to a prior permissive policy. Classify expected denials separately from unexpected failures. A 401 proves no authenticated service access, not network enforcement; a 403 requires its service-specific error reason. A timeout is inconclusive without network evidence.

## CMK audit analysis

Enable Key Vault `AuditEvent` to the new LAW before the CMK request. Prefer resource-specific `AZKVAuditLogs`; if the diagnostic destination uses legacy mode, inspect `AzureDiagnostics` with `Category == "AuditEvent"`. Check actual available schema before assuming a field exists.

Use [key-vault-audit.kql](../scripts/validate/key-vault-audit.kql) locally to examine operations and available identity/network fields. Look for actual operation names such as `KeyGet`, `KeyWrap`, `KeyUnwrap`, not only successful client requests. Retain denied requests and compare operator key-admin windows with isolated service windows.

Log ingestion may be delayed; key operations may be asynchronous/cached. Start with bounded polling (for example, 5-minute checks for an approved 60-minute observation window), recording actual timing. This window is **not** a documented cache expiry guarantee. If no new operation appears, the result is Inconclusive; seek support guidance rather than claiming success or failure. Keep old key versions available for at least 24 hours on rotation.

Diagnostic fields may not expose a PE resource ID. An identity match, an RFC1918-looking caller IP or successful operation with firewall flags is not by itself sufficient attribution. Report the path test Inconclusive if provider-side correlation/configuration evidence cannot close that gap. A VM or cluster Key Vault request is never substituted for a control-plane CMK request.

## Result classification

1. **Officially supported and validated:** affirmative official support for the exact settings/KRC topology plus all relevant runtime/path tests pass.
2. **Functionally validated, official support unconfirmed:** actual CMK crypto operations and private-path evidence pass under exact settings, but official support remains unconfirmed.
3. **Unsupported or not configurable:** confirmed support limitation or no available required configuration established conclusively. A single transient error/permission failure does not establish this.
4. **Inconclusive:** missing environment/test/path evidence, caching ambiguity, failed preflight or unresolved supportability. **Current category.**

Record a separate public-denial outcome if no external test environment is available. Never report fully externally validated public blocking from VM-local tests alone.
